## 三、踩过的坑

### 1. 500 报错，最后发现跑的不是新代码

某天点发布问题一直 500，堆栈里写着 `TODO(S2)：MarkdownBody.ofQuestion 尚未实现`。我一开始以为是业务代码没写完，翻来覆去查逻辑。

实际原因是本地 Maven 仓库里存着一个旧的 `co-qa-domain` jar：启动时只跑了 `-pl co-bootstrap`，没带 `-am`，用的还是上一次编出来的包。

后来养成了习惯：报错先确认现在跑的到底是哪份代码，`mvn install` 带不带 `-am` 差别很大。

### 2. pre-commit 钩子根本没执行

配好 Husky 之后，我故意写了个 lint 错误去测，结果提交照样成功。查了退出码才发现钩子报了 `$'\357\273\277cd': command not found`——`.husky/pre-commit` 文件开头带了 UTF-8 BOM，`sh` 把 BOM 当成命令名的一部分。

删掉 BOM 之后钩子才真的开始拦人。这件事让我明白："配了"和"生效了"是两回事，一定要拿一个必然失败的例子去验。

### 3. 搜"软工"搜不到"软件工程"

我的验收标准里有一条就是搜"软工"能命中"软件工程"，实际测下来一条都搜不到。

原因是 MySQL 的 ngram 分词按两个字切片，"软件工程"切出来是 `软件 / 件工 / 工程`，索引里根本没有"软工"这个词；换成 `LIKE '%软工%'` 也不行，因为"软件工程"里没有连续的"软工"两个字。

这不是代码写错了，是词法检索本身的边界。最后加了一张简称对照表（软工→软件工程 这类五条），检索前先替换成全称。

## 四、我学到了什么

**"能跑"和"跑的是哪份代码"是两件事。** 前面那次 500 花了我大半天，其实第一分钟就该去确认产物是不是新的。

**质量门禁是一条链，不是几条命令。** lint 能过、typecheck 能过、钩子能拦、CI 能跑，这四件事各是各的坑，缺一个"提交被拦"就是假的。

**界面上的小毛病都是工程问题。** 搜索每敲一个字符发一次请求、旧响应回来覆盖新结果、连点按钮重复提交、加载失败后页面上没有任何出路——这些都能复现，不是"样式不好看"。

**分层边界要靠代码表达。** 外部输入校验放在 `of()`，持久化重建放在 `reconstitute()`，脏数据要能被看见，而不是悄悄吞掉。

**改别人的模块要先说一声。** 我在前端 PR 里改了 `Tags`，那是另一位同学负责的上下文，虽然修复是对的，但事先没同步，评审时被点到。

## 五、如果重做一次

1. **先做最小验证，再猜原因。** 服务起不来，先 `curl` 一个接口确认活没活着，不要凭感觉翻代码。
2. **录屏和截图按规范一条条对，录完立刻核。** 我是先录完才去看规范，结果少了两个画面，只能算部分完成。
3. **提交信息一开始就守规范。** `chore(Lab5)`、`docs(Lab4)` 这种 scope 不在允许列表里，也没关联 Issue，后面才发现。
4. **AI 使用的说明当场写。** 拖到最后补，等于让"过程可核查"这件事失效。
