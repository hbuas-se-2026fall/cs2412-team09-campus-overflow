## 三、我踩过的坑

### 1. 「不阻塞合并」等于默许

评审 ADR-009（#22）时我发现 FF 表三条与代码不符，结论却写「不阻塞合并，改完顺手推个 commit 就行」。
PR 被直接合了，错误留在 main 上，**一周后我自己开了 #7 去补**。

**教训**：事实性错误不能挂"不阻塞"。要么直接 `REQUEST_CHANGES`，要么自己开修正 PR。
"不阻塞"只是把问题从评审页搬到了主干分支。

### 2. 覆盖率门禁一开始是摆设

`domain.coverage.minimum` 的值原本是 `0`——门禁存在，但永远不会拦截。

我是先看到配置才发现的，如果没有主动去核，这个"看起来有门禁"的状态会一直持续到答辩。

**教训**：**门禁要能失败才算门禁**。设完阈值必须拿真实代码跑一遍，确认它会红、也会绿。

### 3. `setState` 写在 effect 里

做 US-10 的「我的声誉」卡片时，第一版在 `useEffect` 里同步 `setProfile(null)`，
ESLint 直接报 `react-hooks/set-state-in-effect`：同步 setState 会引发级联渲染。

改成在 `then/catch` 回调里更新，并加了 `cancelled` 守卫，切换账号时旧响应才不会覆盖新数据。

**教训**：前端的 lint 规则不是形式主义，这条如果不改，症状是"偶发闪一下旧数据"，很难查。

## 四、我学到了什么

### 技术

- **分层不是形式**：业务规则放聚合、用例编排放应用层，最直接的回报是 117 个测试 **10 秒内**跑完。
  规则散在 service 的 if-else 里，这些测试就全得启动容器
- **口径要能自证**：Sonar 显示 32.8%、JaCoCo 是 77.2%，两个数字并存。能说清"为什么不同"
  （全项目 8116 行 vs 领域层 602 行）比把数字做漂亮重要——答辩一定会被问到
- **版本标签是快照**：v1.0.0 打在 ADR 修正前 2 小时，发布出去的文档就是旧的那版。
  修完必须重新打点，不能移动已发布的 tag

### 工程

- **评审的写法**：「问题 + 依据 + 建议」三段式。给依据时要能指到具体行、具体断言，
  否则作者只会回一句"我觉得没问题"
- **红灯先分清是谁的**：某天所有 PR 连同 main 的 CI 全红，job 3 秒结束、0 个步骤——
  一看就不像代码问题，而是组织层面的 Actions 配额。**先看现象特征再归因**
- **顺手牵羊的 PR 要拦**：#30 标题写 `ci:`，实际夹了 180 行「通知已读」功能。
  代码没问题，但历史可读性也是质量的一部分

### 协作

- 跨所有权的代码要提前打招呼：`Tags` 是别人名下的领域代码，我在评审里专门提醒要同步，避免积累矛盾
- 群里同步比单点沟通有效：US-13 的前端缺口是"从来就没有"，不是我引入的，说清楚比闷头补更省事

## 五、如果重做一次

1. **从第一个 PR 就立标准**：早期几个 PR 我只留 1–2 条意见，后期才提到 6–8 条。标准应该一开始就顶格
2. **小步提交**：全程 squash 合并导致 `git log` 上每人只有一两个提交，直接踩中 V3「每人每周 ≥3 次有意义提交」
3. **门禁先立、再写业务**：覆盖率阈值应该在第 2 周就定，而不是等 107 个方法写完才回头补
4. **前端多做一点**：我的工作偏后端与质量，课程成员管理页至今没有 UI，答辩演示只能开 Swagger
