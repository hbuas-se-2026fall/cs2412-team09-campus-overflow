# 个人总结 · 黄嘉胜（PO + Dev）

**项目**：CampusOverflow 校园问答平台
**角色**：Product Owner + 后端开发
**团队**：Team 09（5 人）
**周期**：8 周 / 4 个 Sprint

---

## 一、我的职责

作为 PO，我负责：
- 梳理产品 Backlog，把课程要求拆解成 14 个用户故事
- 排序优先级，决定每个 Sprint 进哪些故事
- 主持 Sprint Review，验收每个故事的完成度
- 走查前端交互，确保产品符合预期

作为 Dev，我参与：
- Discovery 上下文的搜索服务实现（US-07）
- Q&A 上下文的提问用例实现（US-02）
- 环形评审中的代码评审

---

## 二、我交付了什么

### 产品侧
- 14 个用户故事的撰写，每个都带 Given/When/Then 验收标准
- 4 个 Milestone 的划分，按 Sprint 粒度组织 backlog
- 6 个上下文标签（Discovery / Q&A / Reputation / Identity / Mobile / Admin），让看板可按领域筛选

### 开发侧
- **Question 聚合根**：标题、正文、标签、课程归属，domain 层零依赖
- **提问用例**：校验标题长度、标签非空、课程存在，抛领域异常
- **搜索服务**：Jaccard 相似度 + 关键词匹配，纯函数可测试
- **相关问题推荐**：侧边栏返回 5 条相似度最高的问题

### 质量侧
- 评审了队友的 PR（环形评审 ①→②→③→④→⑤→①）
- 补了搜索排序的边界测试用例

## 三、我踩过的坑

### 1. 中文分词没想到
Sprint 3 做搜索时，一开始只做了英文分词。测试发现搜"软工"匹配不到"软件工程"，才意识到中文需要分词。临时引入分词库，返工了半天。

**教训**：技术预研要提前到 Sprint 0，不要在 Sprint 内现想方案。

### 2. 权限一开始写在了 controller
Sprint 2 做教师认证时，一开始把"当前用户是不是教师"的判断写在了 controller 层。后来 code review 时 SM 指出，权限校验属于业务规则，应该下沉到 domain。返工了一次。

**教训**：DDD 分层要刻在脑子里——controller 只做参数解析和响应包装，业务规则一律进 domain。

### 3. 看板建错了地方
一开始把项目板建在了自己私人账号下，老师和队友打不开。后来迁到了组织仓库下，又因为默认私有被拦了一次。折腾了两天才把看板、权限、assignee 全部理顺。

**教训**：协作工具第一天就要确认"谁能看到"，不要等截图要交了才发现权限问题。

## 四、我学到了什么

### 产品思维
- 用户故事不是"功能清单"，是"角色 + 欲望 + 价值"三段式。写不好验收标准，后面开发就会跑偏
- PO 不是"什么都要"，是"什么先不做"。学会砍掉 P2 故事，比加需求难多了

### 工程实践
- DDD 五层架构（interface / application / domain / infrastructure / client）真的能让多人并行不打架——每个人守自己的上下文，边界清晰
- CI 从第一天就配上，提交即跑测试，比"最后一天补测试"省心 10 倍
- 环形评审不是走形式——队友真的会指出你没注意到的边界条件

### 团队协作
- 5 个人的团队，每天 15 分钟站会足够对齐，不用开长会
- WIP 限制（In Progress 最多 2 个）真的有用——防止有人同时开 3 个任务，最后每个都卡住
- 环境问题是最大的效率杀手——Docker/WSL 拖了前期整整一周，下次项目开始前先把基础设施搞定

---

## 五、如果重做一次

1. **Sprint 0 做足**：环境搭建、技术预研、CI 配置、看板权限，全部在正式 Sprint 之前搞定
2. **测试先行**：每个故事先写测试用例清单，再写实现，不要"写完再补测试"
3. **移动端早考虑**：响应式布局从第一个页面就开始，不要放到最后一个 Sprint 才返工
4. **文档同步**：ADR、README、changelog 跟着代码一起提交，不要最后补
