## 学到什么

**测试比需求文档好读。**

一开始我按自己的想法写实现，跑测试一片红。后来学会先看断言：标题 10 到 150 字、标签最多 5 个、票值只能 ±1，全在测试代码里。老师已经把规格写好了，先读懂测试比自己瞎猜快得多。

**批了不等于合了。**

有两个 PR 下午两点批完，第二天早上十点才合，中间空了二十多个小时。批的人以为完事了，提的人以为还没批。后来我们在章程里加了条规则：谁批的谁负责直接点合并。

**截图不能加工。**

被打回来过两次。一次是在自己的本地副本上跑的，路径跟主仓库对不上；一次是终端日志太长，我把前面削了还加了两行中文注释，老师一眼就看出不是原始截图。截图必须是合并后 main 上跑出来的，命令要和仓库一致，不能二次修饰。

**红的不一定是代码。**

集成测试全红那次，我以为改坏了。看日志发现 job 两秒就结束了、一个测试步骤都没跑、连日志文件都没有——最后查出来是组织的 GitHub Actions 分钟数用完了。排查问题要先看运行环境，再看代码。

## 做得不好的

**代码写得少。**

107 个方法我只占 7 个。我的时间主要花在配 CI、写文档和跑流程上。答辩如果问到别人负责的那块业务逻辑，我只能讲出大概流程，具体实现细节还得花时间补读。

**跟进进度不够硬。**

中期推进一度停滞了几天。当时我只在群里泛泛提醒了句“大家注意进度”，没单独对齐每个人的进度。问“做完了吗”往往只会得到一句“快了”，应该直接问具体的卡点。

**文档写完的时间偏后。**

很多文档和截图都压到最后两周才收口，导致截图发现环境对不上时还得返工重跑。如果每个 Sprint 结项时就把当期的凭据截好，最后发版收尾会省很多事。

**命令行操作失误过一次。**

建分支的命令其实没成功，我没看终端提示就直接 commit，结果提交落到了本地 `main` 上。虽然后来用 reset 挪回去了，但说明我顺手敲命令时没养成每一步确认分支状态的习惯。

## 如果再做一遍

1. **第一周把规范定死**：PR 模板、分支命名、截图必须来自合并后的 main 且命令与仓库一致，第一天就在仓库里写清楚，省得最后反复返工。
2. **环境参数尽早跑通**：多模块编译的 `-am` 参数、Docker API 的版本兼容，一开始搭脚手架就测通锁死，不要让 CI 连红三天。
3. **答辩前把别人的代码通读一遍**：花时间把另外 100 个方法的调用链过一遍，不能只懂自己负责的 Answer 和 Comment。
4. **写个小脚本抓凭据**：把跑测试、测覆盖率、导出环境信息的命令写成一个脚本，跑完自动保存原生控制台输出，杜绝手动截图带来的路径对不上和格式问题。
