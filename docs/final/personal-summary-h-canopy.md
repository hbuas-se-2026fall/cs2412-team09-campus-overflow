# 个人总结

黄嘉胜（H-Canopy），② 号，SM 兼 Q&A 领域开发。

## 我干的活

代码写了 7 个方法，在 PR #9 里：Answer 的 submit、edit、endorse、softDelete、ensureNotDeleted，加上 Comment.post 和 Tags.names。

印象最深的是 softDelete 那条规则：被采纳的回答，作者自己不能删，课程管理者可以。原因是有人会先让人采纳、拿到分，再把回答删掉。这个坑不是我想出来的，是测试里就这么写的。看过之后才明白「领域规则」不是把 if 写进 service 里那么简单。

除此之外我主要在做流程上的事。

CI 红了三天没人管，最后发现是架构检查那一步少写了 `-am`。改完第一次看到全绿。

分支保护配了 main 和 develop 两条，禁强推、禁删除、要 1 个人批。后来我试着直接 push 被拒了一次，那一下才知道规则是真的在拦人，不是摆着看的。

仓库从我的个人账号迁到了课程组织。迁的时候踩了个坑：组织只允许 Owner 建仓库，我这边一直报没权限，白等了一天。最后是老师建空仓、我们往里推，代价是老的 PR 历史留在了旧仓库。

文档基本都是我写的：需求的故事地图和 14 条 PBI、8 条 Gherkin、领域那边的上下文映射和术语表、事件目录、9 份 ADR、Sprint 0-4 的记录、运维手册。还有打的两个 tag，v1.0.0 和 v1.1.0。

## 学到的东西

**测试比需求文档好读。** 一开始我按自己的想法写实现，写完跑测试一片红。后来改成先看测试里断言什么——标题 10 到 150 字、标签最多 5 个、票值只能 ±1，这些全在断言里。老师已经把规格写好了，我们只是没去看。

**「批了」和「合了」是两件事。** 有一次两个 PR 晚上九点批完，第二天早上十点才合，中间空了二十多个小时。批的人以为完事了，我以为还没批。后来在章程里加了一条：批完的人直接合。

**截图不能加工。** 交上去的截图被打回来两次。一次是命令跟仓库里的对不上，因为我是在自己的副本上跑的；一次是终端日志我把前面的时间戳和线程信息删了，还加了两行中文注释。老师一眼就看出来不是原始终端。

**红的不一定是代码。** 有一次集成测试全红，我以为是改坏了。看日志发现 job 两秒就结束、一个步骤都没跑、连日志文件都没有——是组织的 Actions 分钟数用完了。再往前一次是 runner 的 Docker 升级了，Testcontainers 还在用老版本 API。这两次都不是代码问题，但得会看才知道。

## 做得不好的

前面太松，后面太赶。前三个 Sprint 推进很慢，文档和截图全堆到最后两周补，光是截图就返工两次。如果一开始就按规范来，能省两天。

有个队友三天没有提交也没有评审，我只在群里说了句「大家注意进度」，没单独问。现在想来应该直接问「PPT 写到第几页了」——问「做完了吗」永远得到「快了」。

代码写得少。107 个方法我只占了 7 个，大部分时间在写文档和跑流程。答辩如果问别人负责的那块，我只能讲个大概，讲不细。

还有一次操作失误：建分支的命令其实没成功，我的提交落到了本地 main 上。虽然挪回去了，但说明我串行跑命令时不看每一步的结果。

## 如果再做一遍

第一周就把截图规范、PR 模板、分支命名定死，别等到交之前补。

每周打开一次 Contributors 看谁的数字不对，当场问，别等到回顾会。

挑一块别人负责的代码认真读一遍。现在只能讲自己写的那部分，这个问题答辩前补也来得及，但应该早点想到。
