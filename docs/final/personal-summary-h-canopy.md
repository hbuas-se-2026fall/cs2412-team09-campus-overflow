## 二、我学到什么

### 1. 测试是规格，不是负担

起始代码里 107 个方法是 TODO，但测试全都写好了。我最初的想法是「先写实现，再跑测试看哪不对」，后来发现反了——**测试里的断言就是需求文档**，边界值（标题 10/150 字、标签 5/6 个、票值 ±1）全在断言里，读测试比读需求快得多。

### 2. 「批了」不等于「合了」

最典型的一次：#3、#4 在 10-29 13:43 获批，直到 10-30 10:24 才被合并，**空转 21 小时**。批的人和作者都在等对方。

后来在章程里补了一条：**批准人直接合并，合并前确认 CI 是绿的**。三周内又出现过两次同类空转（#10 挂了 3 天），说明规则写了还得有人盯。

### 3. 证据要比结论先准备好

早期提交的截图被要求返工两次：一次是命令和仓库里的 `package.json` 对不上（跑的是本地副本），一次是终端日志被削掉前缀还加了注释。

**老师不看你说得多好，看证据能不能对上。** 从那以后我的规则是：截图必须来自合并后的 main，一个字的加工都不要。

### 4. 分清「代码问题」和「环境问题」

集成测试突然全红，job 2 秒结束、`steps=0`、没有日志——这是组织 Actions 额度耗尽的特征，不是代码坏了。再往前一次是 runner 的 Docker 引擎升级要求 API ≥ 1.40，而 Testcontainers 用 1.32。

**会看日志、能定位到「不是我的问题」，和能修代码一样重要。**

## 三、我做得不够的地方

**1. 前松后紧。** 前三个 Sprint 推进很慢，文档和截图集中到最后两周补，导致返工次数多。如果从第一次截图就按「合并后 main + 不加工」的规则来，能省下至少两天。

**2. 对一个队友的进度跟得太软。** 有成员连续三天零提交、零评审，我只是在群里提醒，没有当面确认卡在哪里。结果是他的部分靠别人兜底，个人贡献系数会受影响。**催进度要问具体的事（「PPT 写到第几页」），不要问「做完了吗」。**

**3. 代码写得少。** 7 个领域方法，只占 107 个里的一小块，主要精力花在文档和流程上。答辩时被问到细节，我对自己写的那部分熟，对别人的部分只能讲个大概——这是分工的代价，但我本可以多读几遍别人的代码。

**4. 有一次误操作。** 建分支的命令没执行成功，提交落在了本地 `main` 上。虽然及时挪到分支并重置了，但暴露了一个习惯问题：**执行串行命令时不检查每一步的返回值**。

## 四、如果重来一次

1. 第一个 Sprint 就把「截图规范、PR 模板、分支命名」定死，而不是等到交付前补
2. 每周固定看一次 `Insights → Contributors`，谁的数字不对当场问，不拖到回顾会
3. 文档跟代码走同一个 PR，不单独开文档 PR——这次虽然做到了，但有好几次是事后补的
4. 主动认领一块别人负责的代码读一遍，答辩时才能不讲「那是他写的」
