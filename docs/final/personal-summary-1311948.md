## 三、踩过的坑

### 1. 投影器第一版没写测试

当时认为"事件能收到、能处理就行"。评审指出重复事件会重复发通知、索引刷新顺序不对会读到旧数据，旧仓库 PR #10 才补上 15 个测试。

**教训**：事件驱动的组件，幂等和顺序必须先用测试钉住，靠肉眼看不出来。

### 2. 本地能跑 ≠ CI 能跑

集成测试本地通过、runner 上因为 Docker 客户端版本过低失败。我第一反应是怀疑代码写错了，绕了一圈才定位到版本。

**教训**：容器化项目要把"环境版本差异"单独当一类问题排查，先看版本再怀疑代码。

### 3. 长文本往网页里逐字输入

用桌面自动化往 GitHub 评论框逐字输入长文本，内容被截断、按钮坐标点不中，反复试了四次才成功。

**教训**：长内容走剪贴板粘贴 + 快捷键提交，不要逐字符 type。

## 四、我学到了什么

### 工程实践

- **DDD 分层不是纸上的图**：权限校验、状态转移这些业务规则留在 domain / application，controller 只做参数解析，多人并行时边界才不打架
- **事件投影必须幂等**：同一条领域事件可能重复投递，投影器要靠唯一键或状态判断去重，否则用户会收到两条一样的通知
- **文档里的数字要能追到源头**：每个数字后面都要挂"从哪份报告、哪个提交来的"。看①修质量报告时我第一反应是去翻源码，而不是信文档——这个习惯是对的

### 运维

- **容器故障大半不是代码错**：Lab 8 遇到的问题大多出在配置和版本上。`runbook` 的价值是把"下次先看哪里"写下来
- **监控面板不能有 No data**：空面板等于告诉老师"没配好"，宁可少放一个面板，也别留一个查不到数据的

### 团队协作

- **环形评审真的能拦住问题**：我自己的投影器就是被队友评审打回来的，改完确实更稳
- **分支保护 + PR 流程**：`main` 不能直推，逼着每次改动都过一次评审，短期内麻烦，长期省事

## 五、如果重做一次

1. **测试和实现一起提交**：不要再"先跑通、后补测试"，返工的那一轮成本比一开始写测试高
2. **环境差异提前摸底**：本地 Docker 版本、runner 版本、CI 缓存策略，在第一个 Sprint 就对齐
3. **运维手册加"现象→根因"对照表**：现在写的是"出问题执行哪条命令"，缺"什么现象对应什么原因"，真出故障还得自己判断
4. **总结别拖到最后**：这份一页纸压到收尾才写，前面几周的现象和细节已经记不全了
